## 超时链路检查

检查线上 Node 22.23.2 的内置 Undici 6.28.0 时，确认响应头等待和响应体空闲默认均为 300 秒。外层 `AbortSignal.timeout(1200000)` 不会覆盖这两个较短的限制。修复后为后台图片任务和普通 AI 代理显式配置专用 Undici dispatcher，不影响其他下载请求。

| 环节 | 当前限制 | 对超过 600 秒生图的影响 |
| --- | --- | --- |
| 前端提交后台任务 | 无额外应用层总计时器，服务器收到并登记后立即返回任务号 | 浏览器不长时间挂着生成请求 |
| 前端等待后台任务 | 每约 1.5 秒轮询，SSE 更新可提前唤醒，无整体截止时间 | 可继续等待超过 600 秒 |
| 单次查询任务或结果 | 45 秒无响应，单次最长 300 秒，读取最多尝试 3 次 | 只限制某一次 GET，不取消后台生成，也不重复提交生图 |
| 后端连接供应商 | TCP/TLS 建连最长 60 秒 | 从连接建立开始的生成等待另行计时 |
| 后端等待供应商响应头 | `AI_UPSTREAM_TIMEOUT_MS`，线上 1200 秒 | 修复原先隐藏的 300 秒截止 |
| 后端等待供应商响应体 | 同为 1200 秒空闲限制 | 不再由默认 300 秒提前中断 |
| 单次供应商请求总时限 | 1200 秒，覆盖连接、上传、生成和回包 | 超过 600 秒但总时长小于 1200 秒可以继续 |
| 服务器从图床取原图 | `IMAGE_DOWNLOAD_TIMEOUT_MS`，默认 120 秒 | 在供应商完成并返回链接后才开始，与生成时限分开 |
| 前端下载原图 | 45 秒无数据进展、单次最长 300 秒，最多尝试 3 次 | 每个数据块重置停滞计时，失败可继续取回原任务 |
| 生产网关 `/api/image-tasks/`、`/api/ai/`、`/api/` | 读写空闲均为 20 分钟 | 当前后台任务采用短轮询，生成等待主要由后台负责 |
| SSE 会话事件 | 网关 1 小时空闲限制 | 不构成 600 秒生成限制，断线仍可轮询 |
| Node 接收浏览器请求 | 请求体接收默认 300 秒、请求头 60 秒；响应 socket 超时 0 | 这些是上传接收限制，不是上传结束后的生成时限 |

其他分支：Grok Python 传输沿用同一个 1200 秒总时限；自定义模型脚本的 `poll` 默认 300 秒并允许脚本显式指定，这不是当前 T8 后台任务经过的路径。工作台旧缓存下载接口还有独立 20 秒计时器，当前画布新图交付使用 `image-transfer` 的进度超时路径。

验证使用 Undici 提供的测试时钟推进真实 HTTP 客户端的计时器，没有实际等待十分钟或新增付费生图请求。分别复现旧客户端响应头/响应体的 5 分钟限制，并确认新客户端等待 610 秒仍成功、1201 秒触发截止、手动取消及总时限仍有效；加上任务交付和后台回归共 14 项测试通过。
